# Карта проекта «Кинема»

Дата изучения: 2 октября 2026. Основание: исходный код текущей локальной копии, README, конфигурация и тесты. Медицинское содержание внешних источников в рамках этого изучения повторно не проверялось.

## 1. Назначение и границы

Локальный однопользовательский исследовательский MVP измеряет движение верхних конечностей в плоскости видео. Пользователь загружает MP4/MOV/WebM, задаёт анатомическую сторону и контекст задания, получает совместимое видео, скелет, траектории, временные ряды, сравнение сторон и JSON-отчёт.

Расчёты детерминированные. LLM в приложении нет. Выбранное задание и поражённая сторона сохраняются в метаданных; они не меняют формулы анализа и не классифицируют движение.

В отдельном разделе показываются источники и фиксированные литературные правила. Подбор тем опирается на наличие измерений, а не на диагностические пороги. Результаты нового поиска PubMed проверяются библиографически и не используются для автоматического формирования рекомендаций.

## 2. Стек и запуск

Backend: Python, FastAPI, Uvicorn, NumPy, PyAV, MediaPipe, Pydantic, HTTPX. Frontend: React 19, TypeScript, Vite 7, Recharts 3, Lucide. Версии прямых Python-зависимостей закреплены в requirements.txt, полной среды — в requirements-lock.txt. Frontend использует pnpm-lock.yaml; package.json задаёт диапазоны версий.

Production: сначала сборка frontend, затем один процесс Uvicorn на 127.0.0.1:8000. FastAPI подключает frontend/dist при импорте main.py. Если папки нет, API запускается, но UI не обслуживается. Development: Vite на 127.0.0.1:5173, прокси /api на порт 8000.

Расположение данных: STUDY_DATA_DIR, по умолчанию data в корне. Расположение модели: POSE_MODEL_PATH, по умолчанию models/pose_landmarker_lite.task. scripts/download_model.py всегда скачивает модель в стандартный путь и не учитывает POSE_MODEL_PATH.

Нет БД, роутера frontend, менеджера глобального состояния, контейнеризации или CI-конфигурации в отслеживаемых файлах этой копии.

## 4. Жизненный цикл исследования

1. POST /api/studies принимает multipart file, affected_side и task.
2. Проверяются параметры, расширение, наличие модели и отсутствие активного анализа. Файл сохраняется порциями по 1 МБ под случайным 32-символьным hex ID.
3. inspect_video декодирует первый кадр и проверяет первичные ограничения. study.json получает статус queued.
4. ThreadPoolExecutor(max_workers=1) запускает pipeline.run, статус меняется на processing.
5. extract декодирует все кадры. Временная шкала начинается с первого decoded PTS. Отсутствующие и невозрастающие метки отклоняются.
6. MediaPipe требует целые строго возрастающие миллисекунды; pipeline корректирует их отдельно, сохраняя исходное время кадра в результате.
7. Одновременно формируется preview.mp4. Прогресс сохраняется примерно раз в 0,5 с, до окончания ограничен 0,95.
8. После всех кадров сохраняются landmarks, считаются метрики и отчёт с evidence. Статус становится completed. При исключении — failed.
9. Frontend опрашивает выбранное исследование раз в секунду; после completed загружает отчёт и все landmarks.

При старте сервера queued/processing/uploading помечаются failed. Завершённые старые отчёты без поля evidence автоматически обогащаются каталогом. Это не повторный inference и не полноценная система миграций.

## 5. Данные и API

В data/<study_id> находятся original.*, preview.mp4, study.json, landmarks.json, metrics.json, report.json и evidence.json. Запись JSON запрещает NaN, временный файл заменяет целевой атомарно. Набор файлов целиком не является транзакцией.

| Метод и адрес | Поведение |
|---|---|
| GET /api/health | status, model_ready, external_video_transfer |
| POST /api/studies | 202 и начальный статус |
| GET /api/studies | Все study.json, сортировка по created_at |
| GET /api/studies/{id} | Статус и прогресс |
| GET /api/studies/{id}/report | Отчёт; 409, если файла ещё нет |
| POST /api/studies/{id}/evidence | Синхронное обновление контекста, online и topic |
| GET /api/studies/{id}/files/{kind} | original, preview, landmarks, metrics, report, evidence |
| DELETE /api/studies/{id} | 204; 409 при активной обработке или обновлении evidence |

Схема landmarks имеет версию 1.0, итоговый отчёт после enrich — 1.1. metrics.json содержит metrics, asymmetry, normalization и series без собственной версии схемы. Поле reach_duration условное: появляется только при обнаруженном кандидате начала подъёма.

Metric: value, unit, coverage, valid_frames, technical_reliability, status. Пропуск хранится как null. status равен measured либо русской строке причины отсутствия результата. Frontend-типы описывают не все поля JSON и не валидируют ответы во время выполнения.

## 6. Математика и ключевые инварианты

- Девять точек: нос, плечи, локти, запястья и таз с обеих сторон. Точка запястья представляет положение кисти, пальцы и захват не измеряются.
- MediaPipe запрашивает до двух поз; если обнаружено не ровно одно тело, landmarks пустые. Постоянная идентификация человека между кадрами не реализована.
- Допуск точки: confidence >= 0,6 и x/y внутри [0,1]. confidence = min(visibility,presence).
- Перед расчётами координаты переводятся в пиксели: x*width, y*height.
- Точки сглаживаются окном 0,15 с внутри участков без пропусков и разрывов времени >0,25 с.
- Фиксированный масштаб — медианная ширина плеч по видео при покрытии >=60%; ширина <5 px исключается. В реализации ширина вычисляется по сглаженным точкам.
- Метрика выдаётся при >=5 пригодных значениях и покрытии >=60%. High — покрытие >=90%, иначе medium; это техническая полнота данных.
- Угол локтя: shoulder–elbow–wrist, прямой локоть 180°. Угол плеча: hip–shoulder–elbow, рука вдоль корпуса примерно 0°.
- ROM — max-min по пригодным значениям всего ролика.
- Скорость считается по реальным PTS через np.gradient, только на участках >=3 кадров. Нормализованные единицы — ширины плеч и ширины плеч/с.
- Длина траектории суммируется внутри непрерывных участков. Средняя скорость и CV усредняются по кадрам, а не по времени.
- Базовый уровень корпуса и плечевого пояса — медиана первых 0,5 с, нужно >=3 значения.
- Индекс асимметрии: 200*abs(L-R)/(abs(L)+abs(R)), не определён при обоих нулях или пропуске.
- Для каждой стороны выделяется один глобальный максимум плеча. Начало/возвращение — эвристика с порогами +15° амплитуды и +10° относительно базового уровня.

При расширении нельзя подставлять нули вместо отсутствующих данных, соединять производными пропуски или смешивать нормализованные координаты с пикселями.

## 7. Литература и рекомендации

feature_topics использует shoulder_max, elbow_max и wrist_mean_speed обеих рук и наклон корпуса. Наличие любой пригодной метрики руки добавляет широкий набор тем; bilateral_training добавляется при пригодных измерениях обеих рук. Величина асимметрии не управляет выбором метода.

ReviewedCatalogService валидирует источники через Pydantic, выбирает пересечение тем, проверяет reviewed_content и verified и допускает возраст проверки 0–180 дней. Ранжирует по типу, затем году. Дата по умолчанию берётся с системных часов.

grounded_sections требует все указанные в правиле источники и опубликованный статус. PubMed возвращает максимум пять записей за последние пять лет, без передачи значений метрик или ID пациента. Поиск синхронный, с общим network_lock, таймаутом клиента 12 с и кэшем по теме на 24 часа в памяти процесса. Старый онлайн-поиск сохраняется при offline-обновлении; повторный неудачный онлайн-поиск его результаты не сохраняет.

Обновление evidence пересобирает только литературные разделы, сохраняя измерения. Для реального пересчёта метрик из landmarks отдельного API или CLI сейчас нет, хотя данные для этого сохраняются.

## 8. Интерфейс

App хранит всё состояние в useState; эффект polling зависит от ID выбранного исследования. Выбор нового исследования очищает отчёт, кадры, время и ошибки. Графики используют series из отчёта; клик и маркеры событий меняют время видео.

Player рисует исходные landmarks, тогда как графики построены по сглаженным координатам. Поэтому небольшое визуальное несовпадение возможно. Скелет скрывается при отставании кадра >0,15 с. Траектория ограничена одновременно последними 180 кадрами и тремя секундами. Canvas перерисовывается через requestAnimationFrame, включая паузу.

EvidencePanel доступен на обеих вкладках результатов. Источники открываются внешними ссылками. Онлайн-поиск запускается только по действию пользователя. В frontend нет автоматических unit/e2e-тестов.

## 9. Наблюдения для будущих изменений

Это результаты чтения кода, а не подтверждённые эксплуатационные инциденты.

1. **Нормализация и документация:** README описывает исходную медианную ширину плеч, код использует сглаженные точки. Выбор нужно согласовать до изменения формул или сравнения результатов версий.
2. **Готовность результата:** GET report и большинство files проверяют наличие файла, а не completed. Только preview дополнительно требует завершённого статуса. Чтение частично сохранённого результата возможно; evidence update также допускается после появления report.json до финального статуса.
3. **Согласованность хранения:** отдельные JSON атомарны, но report/evidence/metrics/status записываются последовательно. Ошибка между записями может оставить частичный набор. Удаление и некоторые чтения защищены разными по длительности участками блокировки.
4. **Обработка ошибок evidence:** ID добавляется в evidence_active до чтения report.json, а try/finally начинается после чтения. Если чтение повреждённого отчёта выбросит исключение, ID останется в наборе до перезапуска.
5. **Startup:** повреждённый study.json или legacy report.json способен прервать запуск. Глобальный executor создаётся при импорте и закрывается lifespan; повторное использование lifespan в одном процессе не пересоздаёт executor. Комментарий fixture тестов о незакрытии executor не соответствует фактическому lifespan.
6. **Длительность и разрешение:** первичная длительность берётся из контейнера, полный предел дополнительно проверяется по кадрам. Максимальное разрешение ограничено площадью width*height, а не отдельными границами 3840 и 2160. Очень широкое видео может пройти проверку. Preview округляет нечётные размеры вниз до чётных.
7. **Память и скорость:** все landmarks и series держатся в памяти и затем полностью передаются браузеру. SHA256 оригинала рассчитывается через read_bytes, что дополнительно загружает весь файл. Для длинных роликов нужен замер ресурсов до масштабирования.
8. **Frontend:** асинхронное evidence update вызывает общий setReport; смена исследования во время запроса не проверяется перед применением ответа. Возможное смешение выбранного исследования и старого отчёта требует проверки/защиты при изменении UI. В Player нет guard пустого frames внутри цикла траектории.
9. **Форматы:** нет централизованных моделей API для Study/Report, runtime-проверки frontend, общего реестра метрик или полной миграции сохранённых схем. Названия и единицы частично дублируются в App/EvidencePanel.
10. **Развёртывание:** очередь, блокировки и кэш существуют только внутри процесса. Несколько Uvicorn workers нарушают модель координации. Проверка Origin не заменяет аутентификацию.
